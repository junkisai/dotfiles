# design doc を書く

design doc は**合意を取るための文書**であって、完成した機能の報告書ではない。コードを書く前に
書き、レビューで合意してから実装に入る。書くのは実装者。

spec との違いは、決める過程が残ることにある。spec は決まったことの一覧で、後から読んだ人
（次の自分、他のメンバー、AI エージェント）は「なぜこの形なのか」を再現できず、同じ議論を
もう一度やる。design doc は**やらないことと、検討して捨てた案を本文に持つ**ので、

- 実装中にスコープが広がりかけたとき、「やらないこと」に書いてあるかで止められる
- 「やっぱりこっちの作りでは」と思ったとき、すでに捨てた案かどうかが「検討した他の案」でわかる
- AI エージェントに実装させるとき、判断の前提ごと渡せる。仕様だけ渡すと、書いていない部分を
  勝手に埋められる

---

## Step 0: リポジトリの規約を読む

**リポジトリに規約があれば、それがこのスキルより優先する。** 書き始める前に次を確認する。

```bash
ls docs/design-docs/
```

| ある | 読む | 従うもの |
| --- | --- | --- |
| `docs/design-docs/README.md` | 必ず | 書くタイミング・各節の役割・`status` の進め方 |
| `docs/design-docs/_template.md` | 必ず | 節構成。コピーして使う |
| `docs/architecture/*directory-structure*` | あれば | 「置き場所」を決める判断フロー |
| 直近の design doc 1〜2 本 | 必ず | 現行の書きぶり・粒度 |

`docs/design-docs/` が無いリポジトリでは、このスキルに同梱した
[references/template.md](references/template.md) を使い、`docs/design-docs/` を新規に作る。
その場合は README も置くかをユーザーに確認する（規約を明文化しないと次から揺れる）。

---

## Step 1: 書かなくていい変更でないか確認する

| 変更 | design doc |
| --- | --- |
| 画面を足す・URL を増やす | 書く |
| データの持ち方を変える（スキーマ変更） | 書く |
| 既存の画面の振る舞いを変える | 書く |
| ライブラリ・基盤の選定 | 書く |
| 文言修正・スタイル調整・リファクタリング | 書かない |
| バグ修正 | 書かない（原因と直し方は PR に書く） |

**迷ったら書く。** 書き始めて10分で書くことがないなら、それは書かなくていい変更だった、という
判断でよい。書かないと決めたら、その旨を伝えて終了する。

---

## Step 2: ファイルを作る

```bash
date +%Y%m%d
```

`docs/design-docs/<YYYYMMDD>_<topic>.md` を作る。

- `<YYYYMMDD>` は上のコマンドで得た**今日の日付**。記憶で書かない
- `<topic>` は内容がわかる短い kebab-case（英小文字とハイフン）
- 同名のファイルがすでにあるなら、新規に作らず既存を更新するかユーザーに確認する

---

## Step 3: 埋める

現時点でわかっていることを本文に書く。**わからないことを推測で埋めない。**「未決事項」に
質問として書く。

| 節 | 何のためにあるか | 書き方 |
| --- | --- | --- |
| 概要 | ここだけ読んで他の人に説明できる状態にする | 3行以内 |
| 背景 | なぜ今これが要るのか | 困っている人と場面を具体的に。書けないなら、まだ作るときではない |
| ゴール | 達成したかを判定できる形にする | チェックボックスで、検証可能な条件として |
| やらないこと | 実装中のスコープの広がりを止める | 「今はやらない」と「この先もやらない」を分ける |
| 設計 | 画面・URL・置き場所・データ・処理の流れ | 既存コードを読み、リポジトリの実態に合わせる |
| 検討した他の案 | 捨てた案を残す。後から一番効く | **最低1案**。採らなかった理由まで書く |
| 影響範囲 | 壊れうるものを先に挙げる | 既存の画面・データ・運用のどこが変わるか |
| 未決事項 | 決まっていないことを隠さない | 選択肢と、誰といつ決めるかを添える |

- **「置き場所」はディレクトリのパスまで決める。** リポジトリに判断フローの文書があれば、
  それに当てはめた結果を書く。ここで決めておくと実装時に迷わない
- 該当しない節は「なし」と書いて中身を消す。**節ごと消さない。** 空でないことより、
  考えた上で空だとわかることのほうが役に立つ
- `status` は `draft`、`author` はコミット時の author 名

---

## Step 4: 一覧に追記する

`docs/design-docs/README.md` の「一覧」の**先頭**に1行足す。

```md
- [<YYYYMMDD>_<topic>.md](<YYYYMMDD>_<topic>.md) — <1行の説明>
```

---

## Step 5: 未決事項を質問する

作成したファイルのパスを伝え、「未決事項」に挙げた点を質問として提示する。

- 回答が返ったら、本文の該当する節に反映し、「未決事項」から消す
- 「未決事項」が空になったら `status` を `review` に上げる
- **`approved` に上げるのはユーザーの判断。こちらで上げない**
- 合意が取れるまで実装には入らない

### status の進め方

| status | 意味 |
| --- | --- |
| `draft` | 書いている途中。まだ読まなくていい |
| `review` | 読んでほしい。ここで合意を取る |
| `approved` | 合意済み。実装に入ってよい |
| `implemented` | 実装が入った。`pr` に実装 PR を書く |
| `superseded` | 別の design doc が置き換えた。冒頭に後継へのリンクを足す |

**`review` から `approved` に進める条件は「未決事項」が空になること。** 未決のまま実装に入ると、
その判断はコードを書く人の手元で勝手に決まる。

---

## 読みやすさの原則

読み手が一度で理解でき、読み返さずに次の行動が取れることがすべて。推敲は後追いだと高コストに
なるので、**最初からこの原則で書く**。既存の design doc を直す依頼でも同じ原則を当てる。

### 1. 結論を先に置く

「概要」は「これは何・何のためか」を最初の1〜2文で言い切る。背景・経緯・ただし書きは後。

### 2. 一文一義

条件節＋長いリスト＋主節を1文に詰めない。1文に1つの用事。長い文は接続詞（「そこで」「ただし」
「なぜなら」）で切って分ける。

### 3. 「問題 → だから作る」で段落を割る

背景（何が困っているか）と打ち手（だから何を作るか）を別の段落にする。1段落に混ぜると
どちらも薄まる。

### 4. 括弧の連発を避ける

固有名詞のあとに `（…）（…）` と括弧を続けない。視線が毎回止まる。説明が2つ以上あるなら
地の文に出すか箇条書きに逃がす。

### 5. 具体を先に、抽象は後

抽象名詞（「〜の受け取り方」「共通契約」）を連打しない。像を結ばない。まず具体（数字・日付・例）
を見せ、抽象はその後でまとめる。

### 6. 専門用語は前振りしてから出す

話の骨格が定まる前に略語や独自語をいきなり投入しない。「〜といった土台」のように一段まとめる
前置きを付けてから出す。

### 7. 表・数値・具体例で示す

分岐や状態の列挙は、散文よりも**表**が速い。条件 → 結果の対応は1行1ケースで並べる。抽象的な
規則には必ず具体例を1つ添える。数値で裏取りした事実は数値ごと残す。

### 8. コードから読めることは書かない

design doc の価値は**設計判断の理由**にある。SQL の逐語訳やコードを読めば分かることは書かない
（重複してすぐ腐る）。判断の分岐点・トレードオフ・却下した代替案こそ書く。

### 9. 記号を乱用しない

`——` や過剰な `→` で文をつながない。句読点・箇条書き・表で構造を出す。強調は要所だけ太字に
する（全部太字は強調にならない）。

### 10. 日付は絶対日付で書く

「来週」「今月中」ではなく `2026-09-11` と書く。読むのは数か月後の誰かになる。

---

## 実装後は追わない

**`implemented` になった design doc は、その時点の判断の記録として凍結する。** 後から実装が
変わっても書き換えない。書き換えると「いつ何を決めたか」が消える。

方針が変わったら、新しい design doc を書いて古いほうを `superseded` にする。

**恒常的な規約になったもの（構成の規約、依存の向き、命名）は `docs/architecture/` へ移す。**
design doc は「あのとき何を決めたか」、architecture は「今どうなっているか」。常に最新なのは
architecture のほうだけ。

## 書き終えたらの自己チェック

- [ ] 「概要」の3行で、他の人に説明できる状態か
- [ ] 「背景」に、困っている人と場面が具体的に書けているか
- [ ] 「ゴール」が、達成したかを判定できる形になっているか
- [ ] 「やらないこと」に、実装中に広がりそうなスコープが挙がっているか
- [ ] 「検討した他の案」が最低1案あり、採らなかった理由が書けているか
- [ ] 「置き場所」がディレクトリのパスまで決まっているか
- [ ] 該当しない節を「なし」と書いて残してあるか（節ごと消していないか）
- [ ] 推測で埋めた箇所がないか。無いものは「未決事項」に質問として出したか
- [ ] 3行以上の一文、`（…）（…）` の連続、記号の乱用が残っていないか
- [ ] 分岐・状態の列挙が表になっているか。抽象規則に具体例が付いているか
- [ ] 日付が絶対日付か
- [ ] `docs/design-docs/README.md` の一覧の先頭に1行足したか

## 注意事項

- **このスキルでは実装しない。** 合意が取れるまでコードに触らない
- リポジトリに規約があれば、このスキルの記述より規約を優先する
- 完成した機能の説明を後から書くのは design doc ではない。それは `docs/architecture/` か
  PR の本文に書く
