# Design doc

何を・なぜ・どう作るか、採らなかった案、対象外、完了条件を記録する。

- 保存先と既存文書を確認する。`docs/design-docs/README.md` と `_template.md` があれば文書規約として使う。構成の判断に必要なときだけ architecture 文書や過去の例を読む。
- 新規文書の既定は `docs/design-docs/<YYYYMMDD>_<topic>.md`。テンプレートがない場合は [ひな形](references/template.md) を使う。同じ設計の既存文書があれば更新する。
- 会話で決まったことと既存コードで確認できる事実から、必要な節まで下書きする。推測は前提として明示し、合意した事実と区別する。
- ユーザーの判断が必要な未決事項だけを、選択肢・影響・推奨理由とともに聞く。詳細な壁打ちが依頼されている場合は `grilling` を使う。
- 問題、設計判断と理由、検証できるゴール、影響範囲を整合させる。関連する代替案があれば却下理由を残し、埋めるためだけの案や節は作らない。既存テンプレートが節を要求するなら「該当なし」で残す。
- 既存の一覧があれば更新する。`approved` はユーザーの合意がある場合だけ付ける。文書作成だけの依頼なら文書の完成まで、実装も依頼されているなら既存の承認と未決事項に応じて実装へ続く。

完了時は文書のパス、主要な判断、残る未決事項を伝える。実装済み文書は判断の履歴として保ち、後の方針変更は後継文書へ、恒常的な規約は architecture 文書へ記録する。
