# グラレコ生成

文字起こしを読み、**話題を1つも落とさずに**1枚のグラレコ画像（PNG・1280x720）にする。
畳んで絵から落ちた細部は**トピック台帳（Markdown）**に残し、PNG と2点セットで渡す。

目指すのは「かわいいイラスト付きの要約」ではない。
**1枚を見るだけで、何が話され、何が本質的な論点で、何が決まり、次に何をするのかが分かる**こと。

## この段取りにしている理由

- **狙いは「見やすいダイジェスト」ではなく「1枚で全部わかる記録」**。話題を絞って余白のある絵は、その場に居た人の記憶の索引にしかならない。居なかった人が全体を再構成できる状態を目標にする。だから**要素を選ぶのではなく、全部を載せる載せ方を考える**。
- **密度が高いほど、構造がないと読めなくなる**。同じ大きさの枠を並べるだけだと、100項目載っていても目が滑る。**セクションに意味の役割を与え、ストーリーの順に置き、重要な枠を大きくする**。これで密度と可読性は両立する。順番と大きさが情報の強弱そのものになる。
- **1枚の絵に情報の100%は入らない。だから2点で渡す**。4万字の文字起こしを 1280x720 に描くと、載るのは項目100個×14文字＝1,400字ほど。画像が保証できるのは**話題の網羅**であって、各話題の中身は一言に畳まれる。展開・因果・言い回しはそこで落ちる。**落ちた分は台帳に書いて画像と一緒に渡す**。絵で全体像、台帳で細部、という役割分担にする。
- **「話題を全部載せた」は目視では担保できない**。100個以上の項目を絵と突き合わせて抜けを探すのは、照合先の一覧がないと不可能。だから生成の前に台帳を作る。台帳がこのスキルの本体で、絵はその可視化。
- **密度は項目数で稼ぎ、1項目の長さでは稼がない**。画像生成モデルが日本語を崩すのは、長い文を1つの図形に押し込んだとき。4〜14文字のフレーズなら 100 個並べても崩れない。長い文が出てきたら、削るのではなく体言止めに畳む。
- **文章で説明できることでも、構造を絵で説明できるなら絵にする**。共依存は2人を鎖でつなぐ。集客導線は漏斗にする。悪循環は矢印を輪にする。箇条書き3行より1つの図のほうが速く伝わり、面積も食わない。
- **キャンバスは 16:9 横長**。プロンプトでは 1920x1080 を要求し、生成側が返した解像度をそのまま残す（`generate.sh` は比を整えるだけで縮小しない）。限られた面積に全部を入れるので、載せ方の工夫（グリッド表・2カラム・文字サイズの階層）が効いてくる。それでも物理的に入りきらない行は、**黙って消さず台帳に残して報告する**。何を捨てたか黙るのが一番まずい。
- **画像生成モデルは日本語を正確に描ける。ただし条件つき**。検証済みの条件は3つ ―― 短いフレーズに区切る／テキストを「一字一句そのまま」と明示する／どこに何の図形で置くかを全部指定する。配置を指定しないと、生成側が空白を勝手に埋めて頼んでいない英字を混ぜてくる。
- **1回の生成に1〜2分かかる**。当てずっぽうで何度も回すと時間だけ溶ける。プロンプトを作り込んでから1発撃ち、崩れ・抜けが出たら箇所を名指しして直す。

## 全体の流れ

チェックリストとして1項目ずつ消化する。

1. 入力と保存先を確定する
2. 全文を読む
3. トピック台帳を作る（ここが本番）
4. ストーリーの順に並べ、レイアウトへ割り当てる
5. 視覚表現を設計する
6. プロンプトを組み立てる
7. 生成する
8. 台帳と1行ずつ照合して検証する
9. 台帳を Markdown として書き出す
10. 報告する

## Step 1: 入力と保存先を確定する

PNG と台帳 Markdown の2点を、同じ場所に同じ名前で出す。

| 渡され方 | 読むもの | 保存先 |
|---|---|---|
| ファイルパス | そのファイル | 同じフォルダの `<元ファイル名>-grareco.png` と `<元ファイル名>-grareco-topics.md` |
| テキストを貼られた | 貼られた本文 | `~/Downloads/grareco-<内容がわかる語>-YYYYMMDD.png` と同名の `-topics.md` |
| 保存先を指定された | 同上 | 指定どおり（2点とも同じフォルダ） |

同名ファイルが既にあれば `-v2`、`-v3` と足す。上書きしない。作り直しは前の版と見比べたくなるのが常なので、消さずに残す。

作業中の台帳とプロンプトはスクラッチパッドに置き、**台帳だけ Step 9 で保存先にコピーする**。プロンプトは残さない。

## Step 2: 全文を読む

分割せず通しで読む。要約付きの Markdown（`transcribe-audio` の出力など）を渡された場合も、要約だけで済ませず生文字起こしに目を通す。**要約は既に落とした後のテキスト**であり、それを素材にすると落ちたものは二度と拾えない。

読みながら掴むもの:

- **何の場か** ―― 会議 / 対談 / 講演 / インタビュー / コンサル / 1on1 / ふりかえり
- **登場人物と役割** ―― 誰が相談する側で、誰が答える側か。タイトル下の小さな行に入る
- **話の骨格** ―― 時系列で進んだのか、論点が並列に出たのか
- **この回の芯** ―― 一番長く話され、他の話題がそこに接続していく論点。Step 4 で中央に置くもの

拾い出しそのものは次の Step 3 でやる。ここでは全体の形を掴むだけにする。

## Step 3: トピック台帳を作る

**ここが本番。** 全文を頭から末尾まで走査し、**話題・論点・具体例が変わるたびに1行起こす**。この台帳が最終成果物の片方であり、画像の設計図でもある。

**ここでは間引かない。** 絵に載せるかどうかは Step 4 で決める。拾い出しと選別を同時にやると、選別の基準が「なんとなく」になって拾い落としが起きる。

スクラッチパッドに `topics.md` として、次の表で書き出す。

```
| # | 畳んだ表記（4〜14文字） | 詳細 | 種別 | 配置先 |
|---|---|---|---|---|
| 1 | 9/12 東京オフ会 | 9月12日に東京でオフ会。アーキタイプを使った撮影とチーム制作をやる | 連絡 | |
| 2 | 申込締切 8/21（金） | 締切は8月21日金曜。人数確定の都合で延長はしないと念押しがあった | 連絡 | |
```

- **畳んだ表記** ―― 画像に描く文字。4〜14文字（崩れの原因になるので原則守る。2行に折り返すカード本文や背景説明だけ最大24文字まで許容）
- **詳細** ―― 畳む前の中身を1〜3文で。**絵から落ちる情報はここに残る**ので、雑に書かない。数字・固有名詞・言い回しはここに書く
- **種別** ―― 背景 / 現状 / 課題 / 原因 / 気づき / 定義 / 分類 / 手順 / 数字 / 事例 / 発言 / 決定 / 宿題。Step 4 の並べ方と Step 5 の図形がこれで決まる
- **配置先** ―― Step 4 で埋める

書き出すときのルール:

- **落とす判断をここでしない**。「重要じゃなさそう」「細かすぎる」と思っても行を起こす。画像に載るかどうかは Step 4 の話で、台帳からは落とさない
- **1つの話題の中で論点・具体例・数字が分かれたら、行も分ける**。「アーキタイプの選び方」で3つコツが出たなら3行。話題単位でまとめると、そこが台帳の圧縮点になる
- **統合してよいのは同じことの言い換えだけ**。同じ主張が3回出てきたら1行にまとめ、詳細列に「3回言及。とくに強調していた」と残す。**別々の具体例・別々の数字は、似た話題でも統合しない**
- **数字と固有名詞は必ず1行を与える**。「8/21 まで」「55%」「道化師60%」のような具体が、絵を雰囲気ではなく記録にする
- **固有名詞は誤変換を疑う**。人名・商品名・講座名・ブランド名・地名は自動文字起こしで化けやすい。前後の文脈で確信が持てない固有名詞は、絵には載せず台帳の詳細列に「（表記要確認）」と添えて残す。**確信のない固有名詞を絵の大きな文字で描かない**
- **単体で読めない語は落とすのではなく、読める形に書き直す**。「それが大事なんですよね」だけでは通じないなら、前後を読んで「〈何〉が大事」に補って畳む
- **印象的な発言はそのまま1行に**。短くて単体で意味が通る発言は種別「発言」で残し、吹き出しに使う。**本人が言っていない言葉を鉤括弧付きで作らない**
- **長い文は切らずに体言止めへ**。「そもそも何から始めればいいか分からない、という問い合わせが一番多いです」→ 表記「何から始めるか分からない」、詳細に元の言い回しを残す

台帳の行数の目安。**上限として使わない**。入力が濃ければ 200 行を超えてよい。台帳は全部残り、画像に載る分だけが Step 4 で決まる。

| | 目安 |
|---|---|
| 台帳の行数 | 100〜200（入力量しだいで超えてよい） |
| うち画像に載る行 | 60〜120 |
| セクション数 | 6〜9（番号を振る） |
| 日本語の総量（画像内） | 800〜1400文字 |
| 1項目あたりの長さ | **4〜14文字**（カード本文・背景説明のみ最大24文字） |
| 人物イラスト | 2〜4箇所 |
| 小アイコン | 項目の半分以上に添える |

台帳が固まったら自問する ―― **この台帳だけを読んで、その場に居なかった人が話を再構成できるか**。できないなら、行を足すか詳細列を厚くする。

## Step 4: ストーリーの順に並べ、レイアウトへ割り当てる

台帳の「配置先」列を**全行埋める**。ここで初めて、画像に載る行と台帳だけに残る行が分かれる。

**会話の順ではなく、理解しやすい因果の順に並べる。** ただし因果関係と発言の意味を変えてはいけない。

### 4.1 ストーリーの型

セクションは原則この順に置く。使わない段は飛ばしてよいが、順序は入れ替えない。

1. **何の話か** ―― 背景・前提・ここに至った経緯
2. **いま何が起きているか** ―― 現状の棚卸し。事業・テーマが複数あればカードで横並び
3. **具体的に何があったか** ―― 象徴的な事例・エピソード
4. **何が問題で、なぜ起きているか** ―― **この回の芯。画面の中央に、いちばん大きく置く**
5. **どうすることにしたか** ―― 打ち手・決めたこと・合意したこと
6. **次に何をするか** ―― ネクストアクション。担当者と期限つき
7. **この回を一言でいうと** ―― 締めのメッセージ

### 4.2 レイアウトの役割固定

`references/prompt-template.md` の「標準レイアウト」を読んで、次のように置く。

| 位置 | 役割 |
|---|---|
| 最上部中央 | タイトル・日付・登場人物 |
| 左上 | ①背景（なぜこの話をしているか、直近で何があったか） |
| 上部中央〜右 | ②現状の棚卸し（複数テーマはカード横並び） |
| 上部右 | ③象徴的な事例（エピソードカード1〜2件） |
| **中央（最大面積）** | **④この回の芯。論点・本質的な課題・気づき** |
| 右 | ⑤打ち手・決めたこと（チェックリスト） |
| 最下部（全幅） | ⑥ネクストアクション（担当者・期限つき） |
| 右下 | 締めのメッセージ、次回日程 |

- **中央は周囲より明確に大きく取る**。論点が3つあるなら A / B / C の3カラムにして、中央ブロックを画面の3〜4割まで広げてよい
- **視線が左上から右下へ流れるように置く**。番号もその順に振る
- **問題 → 打ち手の対応が見えるように置く**。④の隣に⑤を置き、矢印でつないでもよい
- 話の骨格が時系列そのものだった場合や、論点が並列で順序がない場合は、`references/prompt-template.md` の時間軸型・島型に切り替える

### 4.3 入りきらないとき

- **入りきらないと感じたら、落とす前に詰め方を見直す**。`references/prompt-template.md` の「1枚に全部入れる詰め方」を読む。箇条書きを表に変えるだけで倍入ることがよくある
- **それでも入らない行は、配置先に `台帳のみ` と書く**。消さない。この行は画像から落ちるが Markdown には残るので、情報としては失われない
- **`台帳のみ` に回してよいのは細部だけ**。決定事項・宿題・数字・この回の芯・印象的な発言は必ず画像に載せる。細かい補足や3つ目以降の言い換えから回す

割り付けが終わったら、`台帳のみ` の行数を数えておく。Step 10 で報告する。

## Step 5: 視覚表現を設計する

プロンプトを書く前に、次の3つを決める。決めずに書くと、生成側が勝手に埋める。

### 5.1 因果を図にできる箇所を探す

台帳を見渡して、**箇条書きより図のほうが速く伝わる関係**を探す。`references/prompt-template.md` の「因果を図にする」から型を選ぶ。

- 2者の関係（依存・対立・すれ違い）→ 人物2人＋鎖／糸／矢印
- 絞り込み（集客・選抜・離脱）→ 漏斗
- 悪循環 → 矢印を輪にする
- 連鎖（原因→状態→結果）→ 縦の矢印でつなぐ
- Before / After → 左右に分けて大きな矢印

1枚に**2〜3箇所**入れると効く。全部を図にすると、かえって読めなくなる。

### 5.2 視覚の強弱を4段に決める

| 段 | 対象 | 描き方 |
|---|---|---|
| 1 | タイトル | 極太・最大 |
| 2 | 中央の芯（結論・論点） | 極太のカラー文字、周囲を広く空ける |
| 3 | セクション見出し・決定事項・ネクストアクション | 読みやすい太さ、番号バッジ＋色枠 |
| 4 | 補足・細目 | やや小さめ |

**背景説明（①）は弱くてよい。中央（④）と決定（⑤⑥）を強くする。** すべて同じ強さで描くと、密度が高いほど読めなくなる。

### 5.3 色を4色に決める

**アクセントカラーは4色まで**にし、用途を固定する。セクションごとに色を変えるのは、色が意味を持たなくなるので避ける。

既定の割り当て（`references/prompt-template.md` の「色の使い方」参照）:

- **オレンジ** ―― 重要な論点・強調
- **ティール（青緑）** ―― 現状・事実・アクション
- **ピンク** ―― 感情・人間関係
- **イエロー** ―― 気づき・マーカー

背景は白。線は黒でやや太く、手描きの柔らかさを残す。

## Step 6: プロンプトを組み立てる

`references/prompt-template.md` のテンプレートを埋める。組み立ての勘所:

- **テキストは【】ブロックにまとめ、「一字一句正確に」と明示する**。表のマスも全件書く。省略すると生成側が埋め、そこだけ崩れる
- **配置先にセクション番号を振った行が、全部プロンプトに現れているか数える**。行数とプロンプト中の「」の数が合わないなら、どこかで落ちている
- **セクション見出しも「」付きの描画対象として書く**。`【①冒頭の連絡：左上…】` のようにブロックのラベルに混ぜると、生成側はレイアウト指示と解釈して**見出しを描かない**。ラベルは `【①：左上…】` に留め、中身の1行目に「丸の中に①の番号バッジ、その右に見出しを描く：「冒頭の連絡」」と書く
- **「どこに」「どんな図形で」を全部書く**。書かない余白は生成側が勝手に埋め、頼んでいない英字が混ざる
- **中央のブロックには「いちばん大きく」「周囲より広く取る」と明記する**。書かないと他と同じ大きさになり、芯が沈む
- **冒頭の絵柄指定・可読性指定と末尾の禁止事項は毎回そのまま使う**。削ると写実寄りになったり、密度が落ちたりする
- **項目に小アイコンを名指しで添える**。「カレンダー」「カメラ」「トロフィー」まで書くと絵の情報量が一段上がる

書けたらスクラッチパッドに `prompt.txt` として保存する。日本語の鉤括弧と改行だらけのプロンプトをコマンドラインに直書きするとエスケープ事故が起きる。

## Step 7: 生成する

```bash
~/.claude/skills/grareco/scripts/generate.sh <prompt.txt のパス> <出力PNGのパス>
```

1〜2分かかる。バックグラウンドに逃がさずそのまま待ってよい（タイムアウトは長めに取る）。
成功すると保存先パスと画像サイズを表示する。生成側の実サイズは指定しても揺れるので、
スクリプトが最後に **16:9 へ整え**、**アルファ付きで返ってきたら白を敷いて RGB に落とす**。
**解像度は落とさない** ―― 比からはみ出したぶんを中央基準で削るだけで、拡縮はしない。
縮小すれば小さい文字から読めなくなり、拡大してもボケが増えるだけで情報は増えないため。
プロンプト側にも「1920x1080」「背景は不透明な白」と書いておくと、返ってくる絵が大きくなる。

**PNG ができたことを完了の合図にしない。** 生成側が画像を置いてから正規化が終わるまでに間があり、
その隙に開くと、比を整える前の絵を読むことになる。バックグラウンドに回した場合は
ファイルの存在ではなく**コマンドの終了**を待ってから Step 8 に進む。

失敗したときは終了コードで原因が分かる:

| 終了コード | 意味 | すること |
|---|---|---|
| 3 | codex の認証切れ | **ユーザーに `codex login` を実行してもらう**（下記） |
| 4 | 利用枠の上限 | 時間をおいて再試行することを伝える |
| 1 | それ以外 | 出力されたログパスを読んで原因を掴む |

**認証切れは自分で直せない。** `codex login` はブラウザを開く対話ログインなので、エージェント側から実行しても完了できない。ユーザーに次のように依頼して、待つ:

> codex の認証が切れています。プロンプトに `! codex login` と打ってログインし直してください。完了したら続けます。

codex のトークンは普段は自動更新されるが、リフレッシュトークンごと失効することが定期的にある。生成前に `codex login status` を叩いて弾いているので、2分待たされた末に認証エラーで落ちることはない。

## Step 8: 台帳と1行ずつ照合して検証する

**ここを飛ばさない。** 抜けと崩れに気づかず渡してしまうのが、このスキルで唯一の致命的な失敗。

Read ツールで PNG を開き、**台帳のうちセクション番号を振った行を上から1行ずつ**、画像に描かれているかを確認する。目視で絵を眺めて「だいたい入ってる」で済ませない。台帳の順で探す。

小さい文字は原寸では読み取れない。**セクションごとに切り出して拡大してから照合する**。Python の PIL があれば `Image.open(png).crop((x1,y1,x2,y2)).resize(...)` でスクラッチパッドに出し、それを Read で開く。原寸のまま眺めると、助詞の欠落や1文字の重複を見落とす。

### 文字の照合

- [ ] **セクション番号を振った全行が画像上にあるか**（1行ずつチェックを入れる。見つからない行は行番号を控える）
- [ ] 描かれた日本語が台帳の「畳んだ表記」と一字一句合っているか（表は全マス見る）
- [ ] 頼んでいない英字や意味不明な文字列が紛れていないか
- [ ] 文字が図形からはみ出したり、他の要素と重なったりしていないか

### 構造の照合

- [ ] タイトルが一目で読めるか
- [ ] **中央の芯が、周囲より明確に大きいか**。同じ大きさに描かれていたら、そこを名指しして撃ち直す
- [ ] 左上から右下へ読める並びになっているか
- [ ] 決定事項とネクストアクションが見つけやすいか
- [ ] 1つのセクションだけ肥大化していないか
- [ ] 大きく空いた余白が残っていないか（残っていたら `台帳のみ` の行を繰り上げて撃ち直す）
- [ ] **見た瞬間に「何の回だったか」が分かるか**

### 直し方

**抜けがあったら**、`references/prompt-template.md` の「抜けを足すときの追加プロンプト」で、抜けた行だけを名指しして追加する。
**崩れがあったら**、同ファイルの「崩れを直すときの追加プロンプト」で、崩れた箇所だけを名指しして直す。どちらも全部作り直すと、成立していた箇所まで崩れ直す。

密度が高いぶん指摘箇所は増えるので、**1回のプロンプトで3箇所まで**まとめて名指ししてよい。それ以上あるときは影響の大きい順に3つずつ。

**修正プロンプトは1回だけ撃つ。** 追加プロンプトは既存画像の1箇所を編集しているのではなく、元の絵を見ながら全体を描き直している。2回目を撃つと1回目で直った箇所が崩れ直す。撃ったら照合し、そこで打ち止めにする。**2回目の結果が1回目より悪ければ前の版を採用する。** 詳しくは `references/prompt-template.md` の「修正は1回で止める」を読む。

2回撃っても残る崩れは、その語自体が崩れやすい。台帳側の表記を短く言い換えるか、ひらがなに開いて、次に作り直すときに反映する。同じ絵で粘らない。画数の多い熟語が連続する語、擬態語、半濁点を含む語ほど崩れやすい。

## Step 9: 台帳を Markdown として書き出す

作業用の表をそのまま置くのではなく、**読み物として読める形**に整えて保存先に書き出す。画像で拾えない細部を読む人のためのファイルなので、詳細列が主役になる。

```markdown
# 〈タイトル〉 グラレコ台帳

〈何の場か / 日付 / 参加者〉

グラレコ画像: `〈PNGのファイル名〉`
この台帳は画像の元データ。画像には話題の見取り図が載っており、中身はここに残している。

## ① 〈セクション見出し〉

- **9/12 東京オフ会** 〔画像掲載〕
  9月12日に東京でオフ会。アーキタイプを使った撮影とチーム制作をやる。
- **申込締切 8/21（金）** 〔画像掲載〕
  締切は8月21日金曜。人数確定の都合で延長はしないと念押しがあった。
- **会場は都内で調整中** 〔台帳のみ〕
  会場は都内で調整中。決まり次第アプリで告知するとのこと。

## ② 〈セクション見出し〉
...
```

- **画像のセクション順に並べる**。絵を見ながら読めるようにする
- **各行に `〔画像掲載〕` / `〔台帳のみ〕` を付ける**。どれが絵から落ちたかが一目でわかる
- **詳細は台帳の詳細列をそのまま使う**。ここを削ると、このファイルを作る意味がなくなる
- 末尾に総項目数・〔画像掲載〕・〔台帳のみ〕の件数を1行で書く

## Step 10: 報告する

- **PNG と台帳 Markdown、2つの絶対パス**
- **台帳の行数 / 画像に載った行数 / 台帳のみの行数**（例: 「台帳 148 行、うち画像掲載 96 行、台帳のみ 52 行」）
- **画像から落ちた行のうち主なものを名指しする**。「細部は台帳に」で丸めない。何が絵に載らなかったかを見せて初めて、ユーザーが「それは絵に入れてほしかった」と言える
- 1枚に載せた要素の概要（セクション単位の箇条書き）

## 扱いに気をつけるもの

**センシティブな話題。** コーチング・相談ではメンタル・家族・健康・人間関係・コンプレックスが出てくる。必要以上にセンセーショナルな絵にしない。「メンタルダウン」を描くときも、泣き顔や病的な描写ではなく、**疲れている人物・もやもや・小さな雨雲**程度に留める。当事者が見返すファイルであることを忘れない。

**全体のトーン。** 目指すのは「客観的に整理されているが、人間味がある」状態。避けるのは ―― 企業資料のように無機質／子供向け教材のように幼い／漫画のように演出過剰／SNS投稿のように煽る。

**内容を足さない。** 元の発言にない主張、言っていない引用、確信のない固有名詞を絵に入れない。締めのメッセージも、会話全体から自然に導けるときだけ作る。強引に名言を作らない。
