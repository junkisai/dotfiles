# pr-review スキル

書いた変更を draft PR に出し、実装意図を行に添えて、PR 上のやりとりで合意してから
ready にする。

## なぜやるか

チャットで「できました」と報告すると、依頼者は差分を読む手段がないまま
「たぶん大丈夫」と答えることになる。実装の判断は行に紐づいているので、
行に紐づけて見せ、行に紐づけて指摘を受ける。

場所を PR にするのは、依頼者が普段レビューする場所がそこだからで、
スマホからでも見られ、記録が PR に残る。

## 全体の流れ

1. コミット・push して draft PR を作る（`/pr` スキル）
2. 実装意図を `notes.json` に書く
3. PR の該当行にまとめて投稿する
4. レビューを待ち受ける
5. 指摘を反映する
6. スレッドに返信する（必要な回数だけ 4〜6 を回す）
7. 合意できたら draft を外す

---

## Step 1: draft PR を作る

`/pr` スキルを使う。`git commit` と `gh pr create` は skill-guard Hook が
直接実行を止めるため、**このスキルから叩かない**。

すでに PR がある場合はこの Step を飛ばす。PR 番号は次で取れる。

```bash
gh pr view --json number,isDraft,url --jq '"#\(.number) draft=\(.isDraft) \(.url)"'
```

PR 本文には、依頼をどう受け取ったかを自分の言葉で書く。**ここがずれていれば、
依頼者は差分を1行も読まずに間違いに気づける。** 省略しない。

## Step 2: 実装意図を notes.json に書く

**このスキルの価値の大半はここにある。** 差分を見せるだけなら PR を作れば済む。
判断した理由を添えて初めて、依頼者は是非を判断できる。

保存先は `~/.claude/reviews/<repo>-<branch>/notes.json`（`/` は `-` に置換）。

```json
{"summary": "取得したシークレットの実値を保持し、ログへ出す直前に突き合わせて伏せる作りにしました。\n\n- 各パーサに規約を課すのではなく、**出口の1箇所で伏せる**方式です\n- 伏字は長さに関係なく `***` 固定です\n- `pnpm test` と型チェックは通っています",
 "comments": [
   {"file": "apps/scraper/src/lib/secrets.ts",
    "code": "const MIN_REDACTABLE_LENGTH = 8;",
    "kind": "intent",
    "comment": "8文字未満は伏せない判断にしました。店舗コードや true まで伏字になると失敗調査でログが読めなくなるためです。ここは判断が分かれるので、方針を確認したいです。"}
 ]}
```

| キー | 内容 |
| --- | --- |
| `summary` | レビュー全体の頭に付く。何をしたか、判断の要点、確認してほしい点。テストを通したならその結果も1行 |
| `file` | リポジトリルートからの相対パス。PR の差分に出ているパスと完全一致させる |
| `code` | 指したい行を**行まるごと**引用する。1〜3行。**行番号は書かなくてよい**（行の一部だけでは一致しない） |
| `kind` | `intent`（実装意図）／`applied`・`answered`・`declined`（前回の指摘への対応。Step 6 で使う） |
| `comment` | 本文 |

`code` は本文で照合するので行番号を数える必要はなく、行頭の空白の揺れも吸収する。
照合は行単位なので、長い行でも途中で切らずに丸ごと貼る。

**同じコードが複数箇所にあると先頭に付いてしまう。** 投稿前に警告が出るので、
出たら前後の行を足して一意にする。

### 何を書くか

- **判断が分かれる選択** — なぜその方法にしたか、落とした案は何か
- **仕様の解釈** — 曖昧だった要求をどう読んだか。**依頼者が最も確認すべき点**
- **影響範囲** — ここを変えると他のどこに効くか
- **自信のない箇所** — 「ここは確信がない」と書く。書かないと確認されない

### 書かないもの

- コードを読めば分かること（「バリデーションを追加しました」）
- 全部の行に付けること。読む気を削ぐ

**目安は3〜7件。** 1ファイル1件を機械的に付けない。判断のあった箇所にだけ付ける。

## Step 3: PR に投稿する

まず `--dry-run` で行が解けるか確かめる。投稿はされない。

```bash
D=~/.claude/reviews/<repo>-<branch>
python3 ~/.claude/skills/pr-review/scripts/post_notes.py --notes "$D/notes.json" --pr <N> --dry-run
```

- `diff の中に見つからない` → `code` を `gh pr diff <N>` の出力からコピーし直す
- `同じコードが N 箇所` → 前後の行を足して一意にする

解けたら `--dry-run` を外して投稿する。COMMENT レビュー1本にまとまるので、
依頼者への通知も1回で済む。行を解決できなかったコメントは捨てずにレビュー本文の
末尾へ回るので、黙って消えることはない。

投稿したら PR の URL を伝える。伝えるのは「行にコメントを付けたので、気になる行に
返信してほしい」の一言でよい。**依頼者はエンジニアとは限らない**ので、
notes.json や dry-run といった言葉は出さない。

## Step 4: レビューを待ち受ける

**投稿したら待ち受ける。依頼者に「見たよ」と言わせない。**

Monitor ツールで次を回す（`persistent: true`）。新しいコメントが1件1通知で届く。

```bash
bash ~/.claude/skills/pr-review/scripts/watch_review.sh <owner/repo> <N> ~/.claude/reviews/<repo>-<branch>/seen.txt 30
```

- 自分が投稿したコメントは本文の印で読み飛ばされる。人間の投稿だけが届く
- bot（vercel など）の投稿も既定で読み飛ばす
- 通知は要約だけ。全文は Step 5 で取る

離席が長そうなら張らなくてよい。GitHub 側に残るので取りこぼさない。会話が再開したら、
まず Step 5 の取得を実行して未処理の指摘が無いか確かめる。

## Step 5: 指摘を反映する

全文を取る。`--mark` を付けると、出したものを反映済みの台帳に書く。

```bash
python3 ~/.claude/skills/pr-review/scripts/fetch_review.py \
  --repo <owner/repo> --pr <N> --state ~/.claude/reviews/<repo>-<branch>/applied.txt --mark
```

`diff_hunk` にその指摘が指している差分が入っているので、どの行の話かはそれで分かる。

処理は次の順。

1. **1件ずつ、何を求められているかを判断する。** 修正か、質問か、方針の変更か
2. 判断を要する質問に、推測で答えない。分からなければ聞き返す。
   そこで止まる場合、他の指摘は先に進めてよい
3. **全件を反映してから**、まとめてテスト・型チェックを通す。
   1件ごとに検証をやり直さない
4. 反映しなかったものは理由を書く。**黙って落とさない**

反映できたらコミットして push する。コミットは `/commit` スキルのルールに従う。

## Step 6: スレッドに返信する

**回答をチャットだけに置かない。** 依頼者は自分の指摘がどうなったかを PR で追える
方がよい。指摘のスレッドに直接返す。

```bash
python3 ~/.claude/skills/pr-review/scripts/reply.py --repo <owner/repo> --pr <N> --resolve <<'EOF'
[{"key": "rc:123456", "status": "applied",
  "body": "閾値を4文字に下げました。合わせて短い値の誤検知を…"}]
EOF
```

`status` は `applied`（反映済み）／`answered`（回答）／`declined`（見送り）。
**質問型の指摘には必ず `answered` で回答する。**
`--resolve` を付けると返信したスレッドを解決済みにする。**議論が続きそうなものや
`declined` には付けない。** 依頼者が閉じるかどうかを決める余地を残す。

新しく判断を要する箇所が出たら、`notes.json` に `kind` 付きで足して Step 3 を
もう一度回す。前回の指摘に対する説明が、また行に紐づいて並ぶ。

## Step 7: draft を外す

依頼者が「このまま進めてよい」と言ったら ready にする。

```bash
gh pr ready <N>
```

自分の PR に approve は打てないので、承認は依頼者の言葉で受け取る。
**言われる前に ready にしない。**

最後に PR の URL と、反映した指摘の件数を伝える。
