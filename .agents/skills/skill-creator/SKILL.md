# Skill の作成・改善

その作業に固有の知識、判断基準、ツールの制約だけを残し、目的に合う Skill を作る。

- 既存の依頼と利用例から、対象・入力・成果物・完了条件を特定する。判断を変える不足情報だけを質問する。
- `description` は何をいつ行うかを短く書く。一般的な単語だけで発動させず、似た Skill と混同する場合だけ境界を添える。長い発動例や強制文を並べない。
- 本文には目的・本当の制約・完了条件を残す。複数モードに固有の手順は参照ファイルへ分け、「いつ読むか」をリンクに添える。短い Skill を機械的に分割しない。
- 説明済みの一般知識、冗長な検証、細かな手順の固定を減らす。フック、データ形式、認証、外部操作の権限、復旧条件など、破ると困る契約は維持する。
- ユーザーの既存の承認を尊重し、通常の修正・検証のたびに止めない。未承認の公開や無関係な設定変更へ広げない。スキルの編集依頼をリンク再配置やインストールの依頼とみなさない。
- 名前・description・既存の metadata / invocation policy を保って修正する。説明を短くする目的で既存の明示起動設定を変えない。

## 検証

frontmatter と参照先を確認し、変更したスクリプトがあれば実行する。発動すべき依頼と、似ているが発動しない依頼を照らして境界を点検する。

複雑な手順や重要な境界を変えた場合は、隔離した資料・環境で代表例を評価する。詳しい計測を行うときだけ [評価ガイド](references/evaluation.md) を読む。通常の文章整理に全面的なベンチマークやユーザー評価待ちを必須にしない。

完了時は変更内容、検証結果、未検証の範囲を伝える。実測していない効果や token 削減率を断定しない。
